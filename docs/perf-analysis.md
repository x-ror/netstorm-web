# Базовий аналіз продуктивності

Це вимірювання фази 1: зафіксовано навантаження й ризики, без оптимізацій або змін правил.

## Методика

- Headless: `npm run perf:stress`, Node.js v24.21.0, Linux x64. Сценарій має зерно `24301`, поле `256×256`, 12 AI-суперників, 16 гейзерів, 48 транспортів і 23 початкові будівлі на сторону, 120 зафіксованих пострілів. HP визначень юнітів збільшено лише у fixture до 1 000 000, щоб зберегти кількість сутностей; ігрові дані не змінено. AI працює під час 30 прогрівальних тіків і кожні 30 тіків надсилає ходи всіх 12 сторін. У виміряному інтервалі — 120 тіків; AI під час цих тіків враховано в загальний час.
- Після прогрівання AI додає сутності: в одному зафіксованому запуску було 312 будівель, 576 транспортів, 12 жерців, 16 гейзерів (916 сутностей) і 1142 клітинки мостів.
- Для вимірювання шляху виконується 12 додаткових пошуків через кожну сторону за виміряний тік. Вони не входять у загальний час симуляційного тіку, але входять у метрики pathfinding; вони задають верхнє навантаження пошуку, а не частоту пошуку звичайного матчу.
- Тікання пострілів (`landShots`) викликається безпосередньо всередині `World.step`, окремої зовнішньої межі для його часу немає. Інструментація рахує активні постріли та загальний час тіку, але не приписує їм штучно окрему тривалість.
- Система зберігає до 600 останніх зразків на метрику. Перцентили — nearest-rank. Для AI це час одного рішення однієї сторони; для бою й руху — один виклик обробника сутності, а не сума системи за тік.
- Браузерні показники зібрані smoke-тестом у Playwright Chromium зі SwiftShader: звичайна двостороння місія, 13 сутностей, 46 інтервалів кадрів. Це перевірка інструментації, не навантажувальний прогін 12 сторін на фізичному GPU.

У headless-запусках p99 тіків значно перевищує середнє та p95 через рідкі синхронізовані AI-ходи; середнє може бути більшим за p95 через важкий хвіст. Уже середній AI-виклик перевищив запропонований у попередньому обговоренні бюджет 8 ms; p99 цілого тіку перевищив інтервал фіксованого кроку 100 ms. Хеш обох запусків однаковий (`4035144286`), але час помітно залежить від хоста й фонового навантаження, тому це базова точка для повторного запуску, а не обіцянка швидкодії на обладнанні гравця. В headless-зразках Node.js heap змінювався приблизно від 18 MB до 69.5 MB; короткий прогін і непідконтрольний GC не дають підстав робити висновок про витік.

Heap Chrome `performance.memory` був доступний у smoke: п'ять зразків коливалися приблизно від 21 MB до 47 MB за шість секунд. Інтервали кадрів у smoke включають паузи Playwright між діями й не є частотою кадрів гри в реальному часі; CPU-рендер p95 може бути меншим за середнє через довгий хвіст. Зростання heap на короткому прогоні не доводить витік; для висновку потрібен довший матч із контрольованими GC/heap snapshot. У браузерному smoke не було 12-стороннього матчу, а SwiftShader і headless Chromium не представляють реальний GPU чи цільовий ноутбук. Зовнішній профіль Chrome DevTools (CPU flame chart, GPU, довгий heap snapshot) у цьому середовищі не знімався.

## Ризики масштабування

- **Пошук цілей множить роботу будівель на кількість сутностей.** Для повітряних цілей `airTarget` проходить усі `world.entities` (`packages/sim/src/rules/combat.ts:796-818`); один `tickBuilding` може шукати ціль з `acquire` (`:695-717`). Загальний вибір цілей використовує індекс клітинок для наземних одиниць, отже це не універсальний попарний перебір юнітів. Водночас рикошет сканує всі сутності на влучання (`combat.ts:263-295`), а кожна активна огорожа проходить сутності для кожного свого бар'єра (`:312-343`).
- **BFS має верхню межу в розмірі карти.** `Pathfinder` резервує робочі масиви на `W×H`, обходить доступні клітини та створює координатні пари для перевірки цілі й відновлення маршруту (`packages/sim/src/spatial/pathfinding.ts:84-131`). Транспорти шукають шлях при зміні цілі/маршруту, наприклад повернення додому (`packages/sim/src/rules/movement.ts:148-182,299-314`). Робоча пам'ять BFS повторно використовується, але повторні широкі пошуки лишаються дорогими.
- **AI аналізує світ цілою стороною за один хід.** `aiMove` створює карту загроз, збирає власні транспорти, доступні гейзери та межі території (`packages/sim/src/ai.ts:122-175`); пошук ворожих гармат проходить усі сутності (`:1759-1777`). Клієнт перевіряє кожну сторону щотіку, а всі AI, для яких настав строк, обчислюються синхронно в тому самому фіксованому кроці (`packages/client/src/match.ts:130-145,328-347`).
- **Вартість рендерингу росте з усією сценою.** Зміна рельєфу запускає сканування всіх `W×H` клітин і створення тайлових спрайтів (`packages/client/src/renderer.ts:154-237`). Синхронізація проходить усі сутності; кадри юнітів поза камерою окремо не відсікаються (`:410-500`). Інтерполяція обходить усі рухомі сутності (`:964-985`). Рендерер видаляє і знищує об'єкти зниклих сутностей (`:502-522`), ефекти знищують спрайти після завершення (`:711-729`); повторного використання цих об'єктів не видно.
- **Гарячі контури створюють короткоживучі об'єкти.** `World.step` копіює список сутностей для стабільного порядку (`packages/sim/src/world.ts:639-660`); рендер синхронізує `glides` новими об'єктами координат для кожного юніта (`packages/client/src/renderer.ts:474-479`). Пошук шляху створює тимчасові координатні пари в кожному кроці обходу (`packages/sim/src/spatial/pathfinding.ts:119-131`).
- **Стан видаляється, але сцена й replay мають ціну життєвого циклу.** Транспорт видаляється з мапи сутностей при загибелі (`packages/sim/src/rules/movement.ts:148-152,200-204`), рендерер чистить його display-об'єкти при наступній синхронізації (`packages/client/src/renderer.ts:502-522`). Listener `visibilitychange` знімається при виході з матчу (`packages/client/src/match.ts:322-323,401-406`); явного незакритого listener-циклу в цих межах не виявлено. Натомість `ReplayRecorder` накопичує кадри команд у масиві протягом матчу (`packages/sim/src/replay.ts:77-100`), тож довгі матчі збільшують heap.
- **Мережевого навантаження немає для вимірювання.** Проєкт наразі описує локальний replay, а не мережевий протокол (`docs/architecture.md:128,140`); розмір/частоту мережевих повідомлень і повний стан проти delta sync оцінити неможливо.

## Інструменти

- Headless сценарій: `npm run perf:stress`.
- Браузерна інструментація: відкрити гру з `?perf=1`, знімок поточних метрик отримати в консолі як `window.ns.perf()`.
- `npm run test:browser` перевіряє отримання метрик кадру, тіку, рендеру й draw calls у smoke-сценарії. Для порівняння цільового обладнання потрібні Chrome DevTools-профілі реального 12-стороннього матчу; цієї перевірки тут немає.
