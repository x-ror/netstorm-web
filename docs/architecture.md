# Архітектура NetStorm Web

## Межі модулів

`packages/sim` містить стан світу й правила. Тут немає DOM, PixiJS, запитів HTTP або часу браузера. `World.step(commands)` виконує один тік при 10 TPS. Порядок команд, гравців і сутностей впливає на результат, тому його потрібно зберігати в записах матчів.

Архітектура — модульне детерміноване ядро з контрольованою мутацією стану та окремими адаптерами введення/відображення. Не копіюємо весь світ кожного тіку й не вводимо ECS або ієрархію класів юнітів.

| Модуль `sim/src` | Відповідальність |
| --- | --- |
| `world.ts` | Сховище, setup/debug API, запити та оркестрація тіку |
| `state.ts`, `defs.ts` | Discriminated unions сутностей, параметри правил і визначення юнітів |
| `commands.ts`, `events.ts` | Команди, типізовані результати та payload подій |
| `rules/building.ts`, `rules/bridges.ts` | Перевірка й виконання будівництва |
| `rules/movement.ts`, `rules/priest.ts` | Рух, збір і доставка кристалів, переходи стану жерця |
| `rules/capture.ts` | Захоплення жерця транспортом, вівтар і ритуал жертвоприношення |
| `rules/combat.ts`, `rules/economy.ts` | Вибір цілей, шкода, видача сегментів мостів |
| `terrain.ts`, `mission.ts` | Будівник островів оригіналу й побудова місії з карти: острови, мости, юніти всіх сторін |
| `generate.ts` | Карта сутички з зерна: дві домівки по кутах, острови й гейзери за опціями меню; власний PRNG, детерміновано |
| `rules/fences.ts` | Бар'єри між двома стовпами: пошук пари, смуга, лінія, перетин поля пострілом |
| `spatial/pathfinding.ts`, `cell-index.ts` | Робоча пам'ять BFS і похідний просторовий індекс |
| `view.ts` | Read-only контракт для клієнта |
| `ai.ts`, `ai/params.ts`, `ai/memory.ts`, `ai/threat.ts`, `ai/economy.ts`, `ai/goals.ts` | Комп'ютерний суперник: читає `WorldView`, повертає команди; без випадковості. Рівні складності, пам'ять між ходами (належить клієнтові), карта ворожого вогню й зважений шлях мосту по небу |
| `snapshot.ts`, `replay.ts`, `checksum.ts` | Версії, серіалізація, відтворення й контрольні хеші |

| `presentation.ts`, `stream-batch.ts` | Час показу між тіками (без відмотування на паузі), стани анімації юнітів; буфери меша для потоків Буресили |

Сітка малюється прямокутниками 16×11 у вигляді 3/4, а не ізометричними ромбами; чому — у [client-decisions.md](client-decisions.md). Усе, що залежить від проєкції, проходить через `project` / `unproject`.

`controls.ts` і `hud.ts` отримують лише `WorldView`, спільний `UiState` і callback надсилання команди. Команди накопичуються до наступного тіку. `renderer.ts` не змінює стан світу. Після кожного кроку симуляції, і в наздоганянні теж, `match.ts` забирає події й кличе `renderer.capture()`: рендерер знімає позиції й стан цього тіку, поки спрайти ще на місці, тож вибух за подією `destroyed` і постріл у тік, що проскочив між кадрами, не губляться. Трасер малюється, коли перезарядка стрільця зросла від попереднього тіку, тобто він вистрілив; стрільця, якого на цьому ж тіку знищено, рендерер пам'ятає з попереднього знімка. Снаряд летить у клітинку, яку записала симуляція (`world.shots`), і сідає на тіку її влучання. Панелі — компоненти Svelte: `hud-model.ts` будує з `WorldView` і `UiState` прості дані, компонент лише малює їх, а Svelte оновлює в DOM тільки змінене, тож кнопки не втрачають hover і фокус.

Нові правила додавайте до симуляції. Кнопки, камера й анімації належать клієнту. Рендерер не має змінювати HP, ресурси або положення сутностей. Введення накопичує команди до наступного тіку. `World.apply` також доступний для тестів та налагодження.

`World.view()` повертає live read-only тип, не копію й не runtime sandbox: `ReadonlyMap`, `ReadonlySet`, read-only клітинки та глибоко read-only сутності. Повний `World` залишається доступним лише setup/debug коду та внутрішнім правилам. Мутація світу через debug API під час запису не підтримується.

`World.execute(command)` повертає `{ ok: true }` або `{ ok: false, error: CommandError }`. Legacy `apply` зберігає `null` або той самий типізований код відмови для сумісності. `step` перетворює відмову на типізовану подію `rejected`; пошкоджені внутрішні посилання спричиняють явну помилку. `parseCommand(unknown)` перевіряє зовнішній формат. Цілі координати поза картою залишаються командами, які симуляція відхиляє, а не помилкою декодування.

`World.canBuild` і `World.canDropPiece` є спільними чистими перевірками для preview і виконання; друга використовує ту саму `pieceSite`, що й команда `dropPiece`. Preview використовує footprint визначення юніта й показує недопустиме розміщення червоним; остаточна перевірка завжди виконується на тіку застосування.

## Час і порядок оновлення

`FixedStepClock` накопичує час кадрів і викликає симуляцію кроками по 100 мс. За один кадр допускає максимум п'ять кроків і відкидає надлишковий час. У прихованій вкладці гра призупиняється. Це політика локального матчу, для мережевої гри потрібен планувальник авторитетних тіків.

Спочатку світ застосовує команди, потім оновлює гравців і сутності. Світ робить знімок переліку сутностей перед обходом, щоб нові сутності не отримували зайвий тік у момент створення. Цю семантику потрібно зберегти під час оптимізації.

Рух, бій та економіка не є окремими глобальними фазами: обробник кожної сутності викликається в наявному порядку `Map`. Створені командами сутності входять до переліку цього тіку; створені всередині оновлення — лише наступного. Перевпорядкування систем потребує нової версії правил та окремої перевірки зміни поведінки.

Координати сітки цілі. HP і деякі параметри правил залишаються дробовими. Це не реалізація симуляції лише на цілих числах. Перед мережевим релізом потрібні перевірки повторів у підтримуваних браузерах і версіонування правил та даних.

## Пам'ять і рендеринг

Карта використовує типізовані масиви 256×256 для поверхні, власника й зайнятості. BFS має окремі масиви черги, попередників і міток відвідування, які світ повторно використовує. Кожен світ виділяє для них приблизно 768 KiB. Пошук зберігає порядок сусідів N, E, S, W. Callback мети має бути чистим і не запускати вкладений пошук на тому самому світі.

Рендерер створює на сутність контейнер зі спрайтом, тінню й накладкою і впорядковує контейнери за точкою опори на землі, як вона показана, а не за клітинкою симуляції; літуни — окремою смугою над землею, під ефектами. Земля — окремий спрайт-тайл на клітинку, перебудовується за `terrainRevision`. `addIsland` і успішне розміщення мосту змінюють ревізію; після прямої зміни `terrain` або `owner` редактор чи інструмент налагодження має викликати `invalidateTerrain()`.

Між тіками юніти ковзають від позиції попереднього тіку до теперішнього за `alpha` годинника (одна тікова затримка). Снаряди й болти Енергії рухаються в межах поточного тіку без екстраполяції; їхні влучання, звуки й зникнення належать тіку. `presentation.ts` тримає час показу: пауза, прихована вкладка й скидання годинника заморожують уже показану дробову позу, а не відмотують її назад, і ніколи не програють пропущений час стіни. Там же `VisualStates`: хода починається з першого кадру, коли юніт рушає, а не з `tick % N`; тривалість кадрів лишається тіковою (про частоту кадрів оригіналу ми не знаємо). Смуги здоров'я й лінії будівництва — окремі `Graphics`, перемальовані на тіку й пересунуті на кадрі за спрайтом. Потоки Буресили до будівельних майданчиків `stream-batch.ts` малює двома буферами меша замість окремих об'єктів; буфер росте до 8192 відрізків на штрих і звільняється з сценою. Удар підсвічує спрайт на два тіки, встановлена споруда чи міст на три тіки обведені контуром (не більше 64 клітинок). Числа ці вигадані, див. [client-decisions.md](client-decisions.md).

Камера рухається на частоті кадрів: затиснуті стрілки ведуть її за минулим часом кадру, а не за автоповтором клавіш; перетягування, міні-карта й дискретний зум спрацьовують одразу. Кінцевий зсув камери округлюється до фізичних пікселів, і введення читає саме цей зсув. Інерції, плавного зуму й тряски немає.

HUD і міні-карта оновлюються раз на п'ять тіків і після дій гравця. Клієнт забирає повідомлення через `drainEvents()` після кожного кроку, журнал DOM показує лише події, що стосуються гравця, і зберігає максимум 60 рядків. Події не є записом матчу. Інші споживачі симуляції теж повинні регулярно забирати події.

## Пошук цілей

`CellIndex` групує транспорти за клітинкою. На початку кожного тіку світ перебудовує цей похідний індекс, тому зміни сценарію через публічний `entities` враховуються без окремої синхронізації. Під час руху транспорт оновлює свою клітинку в індексі одразу. Будівлі та жреці залишаються в `occupant`.

Порядок транспортів усередині клітинки відповідає порядку `entities` на початку тіку. Якщо ранній транспорт переходить у клітинку з пізнішим, він зберігає пріоритет. Загиблі або видалені транспорти не є цілями. Індекс повторно використовує масиви клітинок і не входить у хеш стану. Зовнішні зміни стану між тіками дозволені для сценаріїв і налагодження; змінювати стан під час виконання тіку не можна.

Радіусний пошук обходить периметр кожного кільця замість перевірки його внутрішніх клітинок. Він зберігає попередній порядок рядків та координат у рядку. Кількість перевірок координат росте як квадрат радіуса, попередній вкладений обхід ріс як куб радіуса.

`npm run benchmark` порівнює симуляцію з попереднім повним перебором на двох синтетичних сценаріях. Він перевіряє збіг кінцевих хешів, прогріває кожен світ 20 тіків і вимірює наступні 120. Хешування, рендеринг і завантаження не входять у час тіку. Дані часу залежать від машини; CI не перевіряє їх порогами.

Під час локального запуску на Node 24.21.0 медіана тіку для 24 веж і 536 транспортів із цілями в радіусі зменшилась із 1.741 мс до 0.138 мс. Для 24 веж і 512 транспортів поза радіусом зменшилась із 4.804 мс до 0.104 мс. Це вимірювання конкретних синтетичних сцен, а не гарантія FPS браузера.

## Дані та розмір

Кореневі `data/units.json`, `data/maps.json` і `data/missions.json` є джерелом для dev-сервера та production-збірки. Обидва віддають урізані версії (`game-data.ts`): з карт — карти місій, з місій — кампанійні місії з брифінгами. Повний архів спрайтів зберігається в `packages/client/public`; список `TEXTURES` визначає потрібні кадри, а `packages/client/atlas.ts` пакує їх в атласи, які й завантажує клієнт. Додаючи візуальний тип або анімацію, внесіть її кадри до цього списку. За відсутності кадру клієнт показує геометричний маркер.

Збірка копіює лише обрані PNG і створює скорочений `sprites.json`. Архів оригіналу не потрібно видаляти, щоб зменшити розмір гри. `check:size` лише повідомляє розмір збірки (без стиснення і з gzip для JS, JSON, HTML і CSS), обмеження знято: оптимізацію відкладено. Сервер розгортання має увімкнути стиснення, щоб отримати відповідний обсяг передачі.

## Детермінізм і перевірки

Випадкові рішення використовують `World.rng`. Правила не повинні викликати `Math.random()`, `Date.now()` або отримувати час кадру. `hash()` враховує карти, зайнятість, усі поля сутностей і гравців, черги руху, стан PRNG, лічильник ID, переможця та визначення юнітів. Події, ревізії рендерингу, індекс транспортів і робоча пам'ять BFS не входять у хеш.

FNV-1a має 32 біти. Він допомагає виявляти розбіжності, але можливі колізії. Викликайте його на контрольних тіках, а не кожного кадру. Хеш не замінює перевірку команд на сервері або протокол мережевого матчу.

## Комп'ютерний суперник

`aiMove(view, { player, difficulty }, memory)` повертає команди одного ходу. Клієнт викликає його раз на `aiTimeBetweenMoves` секунд місії (за замовчуванням 6), а в сутичці — раз на `DIFFICULTY[level].moveSeconds` (`ai/params.ts`: 8, 5 або 3 с), і подає команди разом із командами гравця на той самий тік, тож replay записує саме команди, а не код AI: зміна AI не ламає записані матчі. AI не змінює світ і не бере `World.rng`; однаковий стан і однакова пам'ять дають однаковий хід. Пам'ять (`ai/memory.ts`: Storm Power на початку й витрати останніх десяти ходів) належить клієнтові, по одній на комп'ютерну сторону, і в snapshot не входить. Карта загроз (`ai/threat.ts`) — сума `dps` ворожих стрільців, що дістають клітинку, виміряна як у `rules/combat.ts` (квадрат, дуга Crossbow, лінія гармати, чотири лінії Sun Cannon); невидимі не рахуються, а з пам'яттю новий ворожий стрілець враховується лише через `reactionMoves` ходів рівня. По ній жрець виходить з-під вогню, Вівтар і Майстерня не закладаються під обстрілом, ритуал чекає, поки біля Вівтаря тихо, а шлях мосту рахує Дейкстра, де клітинка під вогнем коштує `1 + threatWeight × ceil(dps / 10)` (легкий рівень вогонь не зважує). Економіка (`ai/economy.ts`): транспортів — за гейзерами в досяжності, стрілець — за шкодою на Storm Power, накопичення понад три найдорожчі стрільці витрачається на стрільців; за хід кладеться до `actionsPerMove` юнітів різних типів (`Move.laid`), бо той самий тип після встановлення недоступний. Цілі (`ai/goals.ts`): оцінка оборони з тиску ворога (вогонь по своїх, втрати з пам'яті, ворожий міст у тривозі) і рішення про наступ за співвідношенням `dps` з гістерезисом; пам'ять веде перелік своїх будівель (для втрат), простій стрільців (для salvage) і власний PRNG (mulberry32), окремий від `World.rng`. Місійні прапорці `aiAbility`, які ШІ шанує: `!COLLECT_STORM_POWER`, `!ATTACH_TO_ENEMY_ISLAND`, `!SACRIFICE_ENEMY_PRIEST`, `!CONCENTRATE_FIRE`, `!ENCIRCLE_ENEMY_ISLAND`, `!STOP_COLLECTING_FROM_DANGEROUS_GEYSERS`, а також `aiCollectors`, `aiGeyserAttachments`, `aiNEnemy`, `aiSalvageChance`. Розбір і план перебудови AI — у `ai-analysis.md` та `ai-design.md`.

Додатково ШІ: купує повітряний транспорт, коли жодного гейзера не дістати пішки, і шле його до будь-якого гейзера із запасом; ставить базу літунів, коли голова мосту в межах її дальності від цілі (не більше двох); купує зенітки, лише коли в когось із ворогів є повітря; маючи три стрільці, закриває голову мосту бар'єром — добудовує другий стовп у лінію з самотнім або ставить перший (не більше чотирьох стовпів). Хід: вільні транспорти розходяться по своїх гейзерах, до яких можна дійти від Храму (туди, де їх менше); за знерухомленим ворожим жерцем іде один транспорт, якщо ще ніхто не йде; жрець іде до вівтаря, де прикутий полонений. Команди одного ходу перевіряються на тому самому стані світу, тому AI сам веде бюджет Storm Power і зайняті клітинки ходу, щоб наступна команда не розраховувала на вже витрачене. Переможених гравців AI не атакує. Робочі сітки пошуку перевикористовуються між ходами, а сканування обмежене прямокутником власної землі; хід займає в середньому кілька мілісекунд. Міст росте до першої цілі, до якої можна покласти сегмент: найближчий вільний гейзер, а з трьома гейзерами або 4000 Storm Power — ворожий жрець. Відстань рахується пошуком у ширину по небу, тож міст обходить острови. Біля голови мосту AI ставить стрільців (до трьох в обороні, без обмеження поблизу ворога), чергуючи гармати й стрільців з квадратною зоною, і генератори, щоб енергія йшла за мостом. Будівлі не стають поруч із мостом на острові, щоб не перекрити прохід транспортам. Усі пороги вигадані; поведінка оригінального AI невідома.

## Snapshot і replay

`world.snapshot()` повертає відокремлений JSON-safe знімок. `World.fromSnapshot(unknown)` перевіряє формат і створює новий світ, не змінюючи наявний. Знімок містить карти, зайнятість, повні нормалізовані визначення юнітів, сутності, гравців, PRNG, лічильник ID, тік і переможця. Визначення в знімку є версією даних матчу; їх не підміняємо поточним `units.json` при відновленні.

Формат snapshot і replay та правила мають окремі версії (`SNAPSHOT_VERSION`, `REPLAY_VERSION`, `RULES_VERSION`). Несумісні версії відхиляються; автоматичних міграцій поки немає. Масиви сутностей, гравців і визначень зберігають порядок `Map`. Події, ревізії рендерингу, індекси й робоча пам'ять BFS не серіалізуються.

`assertWorldInvariants(view)` перевіряє посилання на власників, типи юнітів, вантажі, носіїв та фактичну зайнятість клітинок. Перевірка виконується на межах знімків і в тестах, а не кожного тіку. Початковий сценарій має перекриті footprint будівель; `occupant` зберігається як окремий авторитетний масив і не реконструюється з припущенням про відсутність перекриттів. Оригінальні визначення можуть мати нульовий footprint, зокрема для небудівельних типів.

Виправлено пов'язані з інваріантами випадки: транспорт із вантажем не приймає новий `collect`; транспорт із вантажем не бере ні другого кристала, ні жерця. Ці команди повертають `bad target`, не змінюючи стан. Жрець не заходить на клітинку гейзера чи іншого жерця, тож не затирає їх в `occupant`. Гейзер має скінченний запас (`stock`) замість таймера. Транспорт пам'ятає свій гейзер у полі `target`, ходить між ним і Храмом, поки запас не вичерпано, а потім переходить до найближчого до Храму гейзера із запасом. Кристал існує лише як вантаж або як предмет на землі: у знищеного транспорту він випадає, і його можна забрати командою `pickupCrystal`. `UnitDef.cls` і `group` є закритими переліками: невідоме значення в даних відхиляється під час завантаження. Знерухомленого жерця забирає ворожий транспорт (`capturePriest`) і приковує на своєму вівтарі; далі жрець власника вівтаря, стоячи поруч, закриває п'ять рун, і лише тоді гравець вибуває. Полонений звільняється повністю здоровим, якщо знищено носія чи вівтар або ритуал зірвано. Логіка — в `rules/capture.ts`. Транспорти й жерці ходять по будь-якій землі, не лише своїй. Бойові будівлі стріляють окремими пострілами з перезарядкою (`cooldown`) і тримають зафіксовану ціль (`target`), поки її можна влучити; Sun Cannon сам повертається до найближчої цілі. Будівництво перевіряє місце й енергію в `rules/building.ts`: юніт стає або на власному острові, або в небі впритул до свого мосту (тоді під ним з'являється острівець), і поруч має бути Храм чи генератор його стихії. Наземний транспорт ставиться на вільну клітинку свого острова й створюється як транспорт; Golem потребує Храму, юніти Wind, Rain і Thunder — Майстерні своєї стихії; класи без правил (повітряні, заклинання) відхиляються. Сегмент мосту має торкатися землі, з'єднаної з Храмом. За знищений ворожий юніт стрілець отримує чверть його вартості; свій юніт можна розібрати командою `salvage` з поверненням до чверті вартості. Сегмент мосту в руці гравця має вік і твердне з часом; покладений раніше стає тріснутим мостом (`Terrain.CrackedBridge`). Знищення або Salvage будівлі тріскає сусідній міцний міст і обвалює тріснутий. Після встановлення юніт того самого типу недоступний `UNIT_REFRESH` тіків (`Player.refresh`). Версія snapshot зараз 7, версія правил — 13.

`ReplayRecorder` записує початковий знімок і впорядковані команди кожного наступного тіку, включно з порожніми тіками й відхиленими ігровими діями. Контрольний хеш додається кожні 50 тіків і завжди для останнього тіку експорту. `playReplay(unknown)` перевіряє безперервність тіків, відновлює початковий світ і відхиляє розбіжність на контрольному тіку. Під час replay події регулярно споживаються.

```ts
const recorder = new ReplayRecorder(world);
recorder.step([{ t: 'movePriest', player: 1, x: 70, y: 150 }]);
const replay = recorder.export();
const restored = playReplay(JSON.parse(JSON.stringify(replay)));
```

Клієнт записує локальний матч у пам'яті протягом життя сцени. Для налагодження доступні `window.ns.match.export()`, `window.ns.world.snapshot()` і `window.ns.playReplay(replay)`. Це API для запису/відтворення, а не UI збережень, постійне сховище чи мережевий протокол. Запис росте з тривалістю матчу; для довгих сесій потрібен окремий потоковий адаптер збереження, не мовчазне обрізання історії.

`npm run check` виконує TypeScript, тести правил і циклу, production-збірку та перевірку розміру. Архітектурні тести фіксують хеші до рефакторингу, порядок оновлення, snapshot continuation, посилання вантажів, відмови декодування та replay checkpoints. Read-only межа має compile-only перевірки. `npm run test:browser` запускає preview на 127.0.0.1:4173 і в Chromium проходить меню, тіки, міст, панель виробництва, вибір транспорту й наказ, паузу, міні-карту, камеру, JSON replay і вихід у меню. `npm test` також запускає тести чистих модулів клієнта (`packages/client/test`). Скрипт використовує Playwright Chromium або `/usr/bin/google-chrome`; інший шлях можна задати через `CHROMIUM_PATH`.

## Наступні зміни

Поточний світ залишається простим сховищем сутностей; правила бою, економіки й руху вже виділені в модулі. Нові здібності додавайте композицією обробників і перевірених визначень, а не успадкуванням класів юнітів. ECS або Web Worker поки не потрібні для наявної сцени.

Перед збільшенням кількості юнітів виміряйте час `step`, BFS і рендерингу на реальних сценаріях. Для великих видимих карт потрібні чанки геометрії та відсікання невидимих частин. Ці зміни мають зберігати порядок вибору цілей і результати повторів.

Система енергії, інтервали пострілів, форма островів та інтервал мостів залишаються наближеннями; повний перелік розбіжностей з оригіналом — у game-rules.md. Архітектурний рефакторинг не підтверджує їхню відповідність оригінальній NetStorm. AI, мережа, повітряні юніти й повні анімації ще не реалізовані.
